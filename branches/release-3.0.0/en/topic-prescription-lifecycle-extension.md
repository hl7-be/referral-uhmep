## Prescription Extension

In some situations, a caregiver needs to keep providing care for the same prescribed service beyond the validity period of the original prescription. eReferral supports this **extension / prolongation** use case.

To support this scenario, the model allows the creation of a **new ServiceRequest that extends the original prescription**.

### Extending a Prescription

When a prescription’s validity period needs to be extended, a **new ServiceRequest** is created.

The implemented 3.0 API links the new prescription to the original through `ServiceRequest.basedOn`. The creation route reads the first reference, with at most one such reference accepted by the creation mapper. The read representation also exposes the extension link through `basedOn`. Sending `ServiceRequest.replaces` alone must not be assumed to create a linked extension.

This is the implemented 3.0 relationship convention, not a claim that `basedOn` and `replaces` have interchangeable FHIR meanings. Validate the complete new request against the target profile rather than assuming that a returned resource can be resubmitted unchanged.

This allows the system to maintain a clear history of prescriptions while preserving the original clinical intent: the original ServiceRequest remains unchanged and represents the **initial prescription created by the prescriber** for its own validity period.

### Role of the New ServiceRequest

The new ServiceRequest represents a new prescription to allow the **continuation of care**, covering a new validity period that follows on from the original prescription.

For continuation of the same care, retain the original patient, requester and prescribed service and supply the new validity period. The creation route requires a complete new prescription, not an instruction to copy the original. Its extension validator checks that the original exists and has the same patient and template. This does not establish that the server automatically copies the requester or enforces that only validity-period fields differ.

### Workflow Tracking

The workflow associated with the prescription is tracked using a new **ReferralTask** resource (generated by eReferral system).

The ReferralTask references the **current active ServiceRequest** through the `Task.focus` element.

### Benefits of This Approach

Creating a new ServiceRequest instead of modifying the original one provides several advantages:

* preserves the **original clinical prescription** and its original validity period.
* maintains a **clear audit trail** of successive extensions.
* avoids ambiguity about which validity period was in force when care was executed.

The API links a new prescription rather than modifying the original validity period in place. Observe the implemented `basedOn` convention described above.
